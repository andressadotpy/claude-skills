# OpenStack Engineer Guidelines

Core policies and community standards for contributing to OpenStack and OpenInfra Foundation projects.

## The Four Opens Principles

All contributions must align with the Four Opens:

### 1. Open Source
- All code and documentation released under open source licenses
- Compatible with Apache 2.0 or OSI-approved licenses
- Users can freely use, modify, and distribute

### 2. Open Design
- Design processes are transparent and accessible to all
- Community members participate in planning and architecture
- Public forums and design summits for decision-making

### 3. Open Development
- Development happens in the open with public code reviews
- Accessible repositories and transparent decision-making
- Lazy consensus and technical committee oversight

### 4. Open Community
- Welcomes diverse contributors regardless of affiliation
- Leadership and influence earned through merit and contribution
- Not based on corporate backing or financial investment

## OpenInfra AI Policy

### Human Responsibility
**CRITICAL**: A human must always be in the loop. Contributors must fully understand and debug any AI-generated code. Treat AI code as untrusted source code.

### AI Tool Categories

**Generative AI** (creates complete code from descriptions):
- Enable features that flag publicly available code matches
- Enable blocking of matching public code suggestions
- Add "Generated-By: [tool-name]" label in commit messages
- Explain prompts and context in comments

**Predictive AI** (suggestive auto-complete):
- Add "Assisted-By: [tool-name]" label in commit messages
- Explain tool usage context

**Assistive AI** (targeted changes like renaming):
- Add "Assisted-By: [tool-name]" label in commit messages

### All AI Contributions Require
- "Signed-Off-By:" label acknowledging full responsibility
- Verification of licensing compatibility
- Configuration for open source compatibility where possible

### Reviewer Requirements for AI Code
- Verify sufficient explanation of AI tool context
- Apply heightened scrutiny to AI-generated content
- Ensure technical and legal standards are met
- Consider removing labels if substantially reworked during review

### Legal Note
Computer-generated work is not considered copyrightable in the United States as of March 2023.

## OpenDev Workflow

### Gerrit vs Pull Requests

OpenStack uses Gerrit's iterative change proposal workflow, NOT GitHub pull requests:

**Key differences:**
- Clone the original repository directly (no personal forks)
- Propose changes via `git push` or `git-review` to Gerrit
- Every commit is a separate change for individual review
- Amend the same commits and push new versions (don't add more commits)
- Results in cleaner branch history with reviewed commit messages

**Benefits:**
- Integrated CI: Tests run on proposal and at merge time
- Speculative execution: Test sequenced changes in parallel
- Cross-project testing: Changes can depend on other repositories
- Reduced fragmentation: Everyone contributes to same repository

### git-review Workflow

```bash
# Setup (one-time)
git clone https://opendev.org/openstack/project-name
cd project-name
git review -s  # Setup git-review

# Making changes
git checkout -b my-topic-branch
# Make your changes
git add .
git commit

# Submit for review
git review

# Addressing review feedback
# Make changes
git add .
git commit --amend  # Amend the same commit
git review  # Push updated version
```

## Commit Message Requirements

### Format

```
Short (50 chars or less) summary

More detailed explanatory text if necessary. Wrap at 72 characters.
Explain what and why vs. how. Can include multiple paragraphs.

Change-Id: Iabc123def456...  # Auto-generated by git-review
Signed-off-by: Your Name <your.email@example.com>
Assisted-By: tool-name  # If using AI assistance
Generated-By: tool-name  # If using AI generation
```

### Required Elements
- **Summary line**: Short, imperative mood ("Add feature" not "Added feature")
- **Body**: Explain what and why, not how
- **Change-Id**: Auto-generated by git-review commit hook
- **Signed-off-by**: Developer Certificate of Origin (DCO) - required
- **AI labels**: If using AI tools (see AI Policy section)

### Best Practices
- Reference bug/story IDs when applicable
- Use proper capitalization and punctuation
- Keep lines wrapped at 72 characters
- Explain context and motivation

## Testing Requirements

### Before Submitting
- Run tests locally to catch issues early
- Ensure new code has test coverage
- Verify existing tests still pass
- Follow project-specific test conventions

### Continuous Integration
- **Zuul CI**: All changes tested automatically
- Tests run when proposed and again at merge
- Must pass all required tests before merge
- Review test failures in Zuul status page
- Use Elastic Recheck to analyze failures

### Test Categories
Different projects have different test suites:
- Unit tests (fast, isolated)
- Functional tests (API/integration)
- Scenario tests (end-to-end)
- Performance tests (when applicable)

## Code Review Process

### Gerrit Review Votes

**Code-Review scores:**
- **+2**: Looks good to me, approved (core reviewers only)
- **+1**: Looks good to me (anyone)
- **0**: No score, informational comments
- **-1**: I would prefer you didn't submit this
- **-2**: Do not submit (core reviewers only)

**Workflow scores:**
- **+1**: Approved for merge (core reviewers only)
- **-1**: Work in progress (blocks merge)

### Review Expectations
- Be respectful and constructive
- Provide specific, actionable feedback
- Acknowledge good work, not just problems
- Focus on code quality, not personal preferences
- Reference relevant documentation/standards

### Responding to Reviews
- Address all feedback (either fix or explain)
- Use reply comments to explain changes
- Update commit message if needed
- Push amended version (don't create new commits)

## Patch Best Practices

### The Right Size
- Keep changes focused on a single logical change
- Don't mix refactoring with new features
- Split large changes into logical patch chains
- Use depends-on tag for related patches

### The Right Content
- Include only necessary changes
- Remove debugging code before submitting
- Don't include unrelated whitespace changes
- Update documentation with code changes

### Patch Chains
For related changes:
- Use Gerrit topics to group related patches
- Use "Depends-On: Change-Id" for ordering
- Keep each patch independently reviewable
- Make dependencies clear in commit messages

## Legal Requirements

### Developer Certificate of Origin (DCO)
All contributions require sign-off, certifying:
- You have the right to submit the contribution
- The contribution is your original work or properly attributed
- You understand it will be public and under the project license

### Individual Contributor License Agreement
Some projects require signing the OpenInfra CLA:
- Review at review.opendev.org on first contribution
- Electronically sign the agreement
- One-time requirement per individual

### License Compatibility
- All contributions under Apache 2.0
- Dependencies must use compatible licenses
- Document any third-party code inclusions
- AI-generated code must comply with AI policy
